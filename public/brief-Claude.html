Driftline product brief

Labels: Built means it exists in this repository and is covered by tests. Proposed means a plan, not a result.

1. What it is

Built. A REST API and dashboard that watches an approved list of web pages and reports the changes that matter. Each check fetches the page politely, reduces it to readable text, masks volatile tokens, diffs it against the last snapshot, scores the change from 0 to 100, and explains the score. Meaningful changes go out as signed webhooks and a daily digest.

3. Why it wins

Most change alerts fail on noise: a page with a clock, a view counter or a rotating ad "changes" on every fetch, and people stop reading the alerts. Driftline separates three things that a naive hash comparison lumps together:

  • Noise: only masked tokens moved (times, counters, session IDs). In the demo data, most of all fetches fall here and produce no alert.
  • Minor: real text changed but scored under the source's threshold, such as a review count ticking up. Recorded, searchable, not pushed.
  • Meaningful: at or above the threshold, with the signals that produced the score (price moved 20%, legal language changed, a section heading appeared).

It is also safe to point at the internet from inside a company: URLs are proposed and approved separately, fetching obeys robots.txt, and the fetcher refuses private and metadata addresses at connect time. The demo numbers come from fictional fixture sites, so they show the mechanism, not field performance.

4. How it is structured

Built. One process holds the API, the scheduler and an in-process rate limiter. That is a deliberate single-instance design for the demo. Scaling out means Postgres for state, a queue for checks, and Redis for rate limits and idempotency keys; the module boundaries (transport, extractor, scorer, store) are already separate so each swap is local.

5. How users discover it

Proposed. Developer discovery first: the public API reference, the OpenAPI document (importable into Postman and code generators), and the GitHub repository. For buyers, a small set of task pages answering specific jobs ("get alerted when a vendor changes its terms", "track competitor price changes") with the live demo embedded as proof, rather than many thin keyword pages.

6. How users engage

Built: the change feed with category and significance filters, word-level diffs, the daily digest, and webhooks for pushing changes into chat or ticketing tools. Proposed: a "not meaningful" button on each change, which doubles as labeled training data for the scorer.

7. How users convert

Proposed. The free path is the public demo plus a self-hosted install. Conversion happens when a team wants hosted checks on its own URLs: sign up, propose sources, an admin approves them, and the first digest arrives the next morning. The first digest is the activation moment.

8. How it makes money

Proposed. Subscription priced by tracked sources and check frequency, with webhooks and approval workflows in team tiers. Price points are a placeholder until validated with design partners.

9. How it should launch

  1. Built: public demo, API reference, OpenAPI document, repository.
  2. Proposed: private beta with a handful of teams tracking their own real pages, each source logged in a rights ledger before its first fetch.
  3. Proposed: measure precision of the meaningful flag from user feedback before charging; publish the method and the result.

10. How it should improve after launch

  • Tune scoring weights per category from the feedback labels; report precision per category.
  • Visual diffs from screenshots for pages where layout carries meaning.
  • PDF and JSON sources (terms often ship as PDFs; APIs as JSON).
  • Multi-instance deployment: Postgres, a job queue, and a shared rate limiter.

Other verticals

The pipeline is page-agnostic; only the fixture sites and keyword lists are specific. The same engine fits regulator guidance pages (category keywords for effective dates and obligations), public grant and procurement notices (deadlines and amounts as extracted facts), and school or municipal policy pages (meeting dates and fees).
