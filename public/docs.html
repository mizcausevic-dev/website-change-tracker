Driftline REST API

Track an approved list of web pages, store normalized snapshots, score every change for significance, and deliver digests and signed webhooks. Base URL: . Machine-readable description: OpenAPI 3.1.

Quickstart


    


    
Authentication and scopes

      
Send an API key as Authorization: Bearer <key>. Keys are stored as SHA-256 hashes, so a database leak does not leak usable credentials. Each key carries scopes; a request without the right one gets 403 with WWW-Authenticate: Bearer error="insufficient_scope", scope="…" (RFC 6750).

      
The public demo key wct_demo_public_explorer_key has sources:read, sources:propose, changes:read, checks:run, digests:read and stats:read. Approving sources, editing them, and managing webhooks need an admin key.

    


    
Errors

      
Every error is an RFC 9457 problem document with Content-Type: application/problem+json. Switch on type, not on title. request_id matches the X-Request-Id response header and the server log line.


{
  "type": "https://github.com/mizcausevic-dev/website-change-tracker/blob/main/docs/problems.md#validation-error",
  "title": "Request body failed validation",
  "status": 422,
  "detail": "2 field errors.",
  "instance": "/v1/sources",
  "request_id": "6c21250a-410a-4daf-8857-0a180a23816f",
  "errors": [
    { "field": "url", "message": "must be a public address" },
    { "field": "min_signficance", "message": "unknown field" }
  ]
}

      
Unknown fields are rejected, not ignored: a typo like min_signficance fails loudly instead of silently using the default.

    


    
Pagination

      
Lists return { data, page: { limit, has_more, next_cursor }, links } and an RFC 8288 Link: <…>; rel="next" header. Cursors are opaque. IDs are ULIDs (time-ordered), so the next page is WHERE id < cursor: stable while new rows arrive, unlike offset paging.

    


    
Conditional requests and concurrency

      
Every successful GET has a strong ETag. Send it back in If-None-Match and you get 304 Not Modified with an empty body when nothing changed. The dashboard polls this way.

      
PATCH /v1/sources/{id} takes JSON Merge Patch and requires If-Match. A missing header is 428; a stale one is 412, so two editors can't overwrite each other. Status changes are not patchable: they go through the approve, reject, pause and resume actions, which record who reviewed what and when.

    


    
Idempotency

      
Every POST accepts Idempotency-Key. A retry with the same key and body replays the first response with Idempotent-Replayed: true; the same key with a different body is 422. Keys are scoped to the API key and kept for 24 hours.

    


    
Asynchronous check runs

      
POST /v1/check-runs returns 202 Accepted with Location and Retry-After. Poll the location until status is succeeded or failed. The fetch happens off the request path, so a slow site never ties up an API connection.

    


    
Content negotiation

      
GET /v1/changes/{id} serves JSON with word-level hunks by default, or a unified diff for Accept: text/x-diff. GET /v1/digests/{id} serves JSON, the email HTML (text/html) or the text part (text/plain). Anything else is 406, and responses carry Vary: Accept.

    


    
Rate limits

      
Limits are per key and client, as a token bucket refilled continuously. Responses carry RateLimit-Limit, RateLimit-Remaining and RateLimit-Reset (seconds until the bucket is full). A 429 carries Retry-After. Failed authentication is limited separately per client to slow key guessing.

    


    
Webhooks

      
Events: change.detected (meaningful changes by default; see filters below), digest.ready, check_run.completed. Deliveries are signed with the Standard Webhooks scheme. The signing secret is shown once, when the endpoint is created. Failed deliveries retry after 1 minute, 5 minutes, 30 minutes, 2 hours and 6 hours, then stop.


import { createHmac, timingSafeEqual } from 'node:crypto';

// Verify a Driftline delivery. `secret` is the whsec_… value returned at creation.
export function verify(secret, headers, rawBody) {
  const id = headers['webhook-id'], ts = Number(headers['webhook-timestamp']);
  if (!id || !ts || Math.abs(Date.now() / 1000 - ts) > 300) return false; // reject replays
  const key = Buffer.from(secret.replace(/^whsec_/, ''), 'base64');
  const expected = Buffer.from('v1,' + createHmac('sha256', key).update(`${id}.${ts}.${rawBody}`).digest('base64'));
  return headers['webhook-signature'].split(' ').some((sig) => {
    const got = Buffer.from(sig);
    return got.length === expected.length && timingSafeEqual(got, expected);
  });
}

    


    
Webhook filters

      
Each subscription can route change.detected with a filter: min_significance, categories, source_ids and tags. All listed conditions must hold; within a list, any value matches. Without a filter a subscription receives only meaningful changes, using each source's own threshold. min_significance replaces that rule for one subscription, so a legal endpoint can receive every edit to terms pages while an on-call endpoint only hears about status changes.


{ "url": "https://legal.example.com/hooks/driftline", "events": ["change.detected"],
  "filter": { "min_significance": 0, "categories": ["legal"] } }

      
PATCH /v1/webhooks/{id} takes JSON Merge Patch with If-Match: filter merges key by key, a key set to null is removed, and "filter": null clears it. POST /v1/webhooks/{id}/test sends a signed webhook.test event immediately so you can check signature verification.

    


    
Ignore-rule preview

      
POST /v1/sources/{id}/ignore-preview replays candidate ignore_patterns over the stored snapshots of the source's last 50 changes and reports which changes they would have suppressed, and how many of those were flagged meaningful. It reads stored text only and changes nothing, so the read-only demo key can use it. CSS selector rules cannot be replayed this way because snapshots keep text, not HTML.

    


    
Feedback on the meaningful flag

      
PUT /v1/changes/{id}/feedback records your verdict (meaningful or not_meaningful) as a sub-resource you own: 201 the first time, 200 when replaced, with GET and DELETE on the same URL. One verdict per API key and network address per change (IPv6 grouped by /64), so clients behind the same NAT share one label. On the demo, labels expire after 24 hours, with at most 200 per change. The stats overview turns these labels into precision per category; with no labels it reports null, not an estimate. On the public demo the labels come from visitors and describe fictional sites, so they show the mechanism, not field accuracy.

    


    
Change history export

      
The changes collection is also available as CSV (Accept: text/csv) or NDJSON (Accept: application/x-ndjson), with the same filters and cursor pagination: pages of up to 1,000 rows, next page in the Link header. It needs the changes:export scope. Cells that a spreadsheet would evaluate as formulas are prefixed with an apostrophe. The export reflects what this deployment stores: the public demo keeps 30 days in memory, so it is a working copy, not an archival record.

    


    
How pages are fetched

      
Only approved sources are fetched. The fetcher identifies itself as DriftlineBot/1.0, obeys robots.txt (RFC 9309), sends If-None-Match / If-Modified-Since, follows at most five redirects on the same site, caps responses at 2 MB after decompression, and resolves DNS through a guard that refuses private, loopback, link-local and metadata addresses at connect time. The guard is checked inside the socket's DNS lookup, so a name that re-resolves to an internal address between validation and connection is still refused.

      
A meaningful change is one whose significance score reaches the source's min_significance. Each change lists the signals behind its score.
